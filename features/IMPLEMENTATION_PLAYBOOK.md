# Implementation Playbook

How every feature in this repo is built. Written after Feature 01, where building the
whole feature in one pass hid a dozen bugs until the end. Each rule below exists
because breaking it cost us something in Feature 01. Feature design docs say *what* to
build; this file says *how*.

## 1. Deliver in slices
- Every feature is split into **slices of about 1–3 hours**, written down in
  `features/NN-*.slices.md` before any code. Each slice is independently mergeable:
  schema, code, tests and docs land together, and `main` is green after every slice.
- **One slice per session.** Finish it, run the full gate (§6), commit, push, confirm CI
  is green, then start the next. Never start slice N+1 on top of an unverified slice N.
- A slice that grows past ~3 hours is split, not pushed through.
- If a slice uncovers a design flaw, fix the design doc first (one line under
  "Design amendments" in the slices file), then the code.

## 2. Test against the real thing
- **Real PostgreSQL, real Redis, real broker.** Feature 01 had a factory test on SQLite
  (it hid a Postgres-only constraint) and dispatch tests with a `MagicMock` task (it
  could not catch serialisation or after-commit timing). Mocks are for third-party
  HTTP only (respx), never for our own database or queue.
- **Prove every guard can fail.** For each new check (a CHECK constraint, a lint rule,
  a coverage gate, a boundary script) add a negative test or run a deliberate
  violation once. Feature 01's coverage gate measured zero files and passed; the fetch
  boundary was only trusted after a probe file failed it.
- **Reader/writer agreement.** When a query assumes something about a column (it is
  set, normalised, non-null), find the writer and test the pair together. Feature 01's
  flag names were normalised on read but not on write, so a flag could silently
  never turn on. Enforce the assumption in the database where possible.
- Run the real process at least once per slice that touches runtime wiring: uvicorn,
  a Celery worker, the seed CLI. Feature 01's worker PII leak and missing access logs
  only showed up in a real process.

## 3. Database and migrations
- **Alembic autogenerate misses CHECK constraints** and can misreport partial-index
  predicates. Hand-write those parts, keep the autogenerated revision id, and after
  every migration run `upgrade head → downgrade base → upgrade head` plus
  `alembic check`.
- Name every constraint through the metadata naming convention (`op.f(...)`), so
  downgrades drop exactly what upgrades created.
- Background, admin and system writes never touch a row's `updated_at` lock token
  (Feature 01 §5). Test it explicitly for every such write path.
- Anything that must hold for all future tables (cascade rules, enum CHECK parity) gets
  an **introspection test** that walks the live schema, so later features cannot forget it.

## 4. Data files and encoding
- All text files are UTF-8 with LF line endings (`.gitattributes` enforces LF). Read
  and write files with an explicit `encoding='utf-8'`: on Windows the default is
  cp1252, which corrupted a `§` in Feature 01 and broke Alembic.
- Bundled datasets record their source, licence, attribution text and the command
  that rebuilds them. Never commit data we are not licensed to redistribute.
- Generated demo data must never resemble real people, businesses or vehicles closely
  enough to be mistaken for them (plates, names, addresses).

## 5. Security and privacy defaults
- No realistic-looking fake secrets in tests: generate them at runtime
  (`secrets.token_hex`), or gitleaks fails CI.
- Personal data (emails, phones, VRMs, full postcodes) never reaches logs; the
  redaction pipeline catches most of it, but do not log it on purpose.
- Pin every new image and dependency version; nothing on `:latest` (Feature 01's MinIO
  images vanished from both registries).
- Destructive or production-affecting commands require explicit flags, log the
  operator (OS user, never an email), and refuse by default.

## 6. The gate: run before every commit
```sh
cd backend
uv run ruff check app tests && uv run ruff format --check app tests
uv run pyright app
uv run lint-imports --no-cache --no-logo
python ../ops/ci/check_celery_dispatch.py
uv run pytest --cov=app/core --cov=app/services --cov=app/modules --cov-fail-under=85
uv run alembic upgrade head && uv run alembic downgrade base && uv run alembic upgrade head && uv run alembic check
cd ../web && npm run typecheck && npm run lint && npm run test:coverage
make api-types && git diff --exit-code -- web/lib/api   # contract unchanged or regenerated
```
Plus a gitleaks scan of what is about to be committed. CI runs all of this too, but CI
is the backstop, not the first time the code is checked.

## 7. This machine
- About 8 GB RAM, often under 1 GB free. Do not run `pytest -n auto` with coverage
  locally (workers get OOM-killed); use `-n 2` or single-process. Run 50k-row perf
  datasets in the nightly CI job, not locally by default. A segfault or a crashed
  `node`/`pyright` is probably memory: check free RAM before debugging code.
- Use `127.0.0.1`, never `localhost` (IPv6 hang).
- The test stack runs on the `.env.test` ports
  (`docker compose -p autotrader-foundation-test --env-file .env.test up -d --wait`).
  If a container is healthy inside but refuses host connections, restart that
  container: it is a Docker Desktop port-forward glitch, not the app.
- No `gh` CLI and the repo is private: ask the user to check the Actions tab after a push.
